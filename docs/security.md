# Безопасность: что делает каждый слой

> **Статус 04.11.2026: проект схемы, не проверенная инструкция.**
> Раздел 3 ниже исторический: EFI-подпись и подписанная политика PCR — разные вещи.
> Прежнюю TPM-enroll-команду **не выполнять** до проверки генерации/доставки PCR-подписей,
> формата ключа и измерений используемого загрузчика. Гарантии про обновления BIOS,
> номера слотов, автоматический fallback и PIN после открытия крышки не испытаны.
> Актуальные ограничения — в `../PLAN.md` и `../README.md`; независимую фразу LUKS сохраняем.

Машина: ThinkPad T14 Gen 1 (AMD), 32 ГБ RAM, TPM 2.0, UEFI, один диск, Windows стирается.
Модель угроз: кража ноутбука целиком, снятие/копирование диска, доступ посторонних
в общежитии/колледже/поездке. Не спецслужба с SPI-дампом и не человек, который знает PIN.

---

## 1. Цепочка загрузки

```
UEFI firmware
  │ Secure Boot: проверяет подпись загрузчика ключами из NVRAM
  ▼
systemd-boot (lanzaboote) на ESP 2 ГБ
  │ грузит UKI: ядро + initrd + cmdline одним подписанным файлом
  ▼
initrd (systemd stage 1)
  │ просит у TPM2 ключ диска, проверяя PCR 11 и подпись UKI
  ▼
TPM2 отдаёт ключ по PIN
  ▼
LUKS2 cryptroot → LVM (pool) → btrfs root → systemd → SDDM
```

На экране: логотип Lenovo → меню systemd-boot с поколениями → `Please enter LUKS2 PIN
for cryptroot:` → 5–15 сек → SDDM.

## 2. LUKS2: два слота

| Слот | Что это | Когда используется |
|---|---|---|
| 0 | парольная фраза (4 слова латиницей) | TPM отказал, диск вставили в другой ПК, восстановление |
| 1 | TPM2 + PIN (4 слова, **отдельно** от фразы LUKS) | обычная загрузка |

PIN — не ключ диска, а разрешение чипу его отдать. Перебор упирается не в энтропию,
а в anti-hammering TPM: после серии неверных попыток чип блокируется на время.
Фраза LUKS — единственный путь восстановления, её копия в Bitwarden и на бумаге.

Ограничение: initrd работает в US-раскладке, ввод вслепую. Поэтому и фраза, и PIN —
только латиница/цифры/дефис. Четыре слова ~32 символа набираются медленно; каждая
ошибка приближает блокировку TPM.

## 3. TPM: вариант B (PCR 11 + публичный ключ)

Запечатывание варианта A (PCR 7) ломается после обновления BIOS. Вариант B привязывает
ключ к подписи UKI, а не к состоянию прошивки:

```bash
sudo systemd-cryptenroll \
  --tpm2-public-key=/var/lib/sbctl/keys/db/db.pem \
  --tpm2-public-key-pcrs=11 \
  --tpm2-with-pin=yes \
  /dev/nvme0n1p2
```

- Политика подписи хранится в LUKS-токене, а не в crypttab.
- UKI при каждом rebuild пересобирается и подписывается тем же ключом → пере-enroll
  после обновления ядра не нужен.
- Обновление BIOS PIN не ломает: PCR 7 в политику не входит.
- В crypttab достаточно `tpm2-device=auto`. Опция `tpm2-with-pin=` — флаг
  `systemd-cryptenroll`, а не crypttab; `tpm2-pin=` нужен только если метаданных в
  токене нет.

Ограничение: откат на старое подписанное поколение из меню возможен — TPM увидит
валидную подпись. Требует физического доступа и перезагрузки; закрывается отдельно
(политика на PCR 4/5 или запрет меню поколений).

## 4. Secure Boot

Ключи: **только свои**, без Microsoft (`sbctl enroll-keys` без `--microsoft`).
MS-ключи означают доверие любому подписанному Microsoft загрузчику: с физическим
доступом через shim + MokManager можно записать свой ключ и загрузить кейлоггер.
Без них грузится только наш UKI. Если после включения SB откажет железо (Wi-Fi, док,
fwupd) — добавить MS-ключи повторным enroll в Setup Mode.

Порядок (нарушение = не грузящийся ноутбук):

1. Установка с `secureBoot = false` (systemd-boot).
2. `fwupdmgr update` — прошивка обновляется до включения SB.
3. `sbctl create-keys`.
4. `secureBoot = true` в `modules/boot.nix` → rebuild → перезагрузка (SB ещё off):
   проверяем, что lanzaboote грузится и `sbctl verify` показывает signed.
5. `sbctl enroll-keys` (без Microsoft) → перезагрузка → `sbctl status` (SB enabled).
6. Только потом TPM-enroll.

Ключи записываются ПОСЛЕ подписанного загрузчика: `enroll-keys` ставит PK, и firmware
включает Secure Boot на следующей загрузке. Если UKI ещё не подписан — кирпич до сброса
ключей в BIOS.

Откат: BIOS → Secure Boot off / Setup Mode, загрузка с флешки, `secureBoot = false`.

## 5. Снапшоты и обслуживание

- btrfs-сабволюмы: `@` (/), `@home`, `@nix`, `@var`, `@snapshots` (/.snapshots).
- snapper: часовые (5), дневные (7), недельные (4) снапшоты корня. `/home` и `/nix` —
  отдельные сабволюмы и в снапшот корня не попадают.
- `services.btrfs.autoScrub` — ежемесячная проверка целостности.
- Снапшот — не бэкап: он лежит на том же диске.

## 6. Крышка и гибернация

`HandleLidSwitch = "suspend-then-hibernate"`, `HibernateDelaySec=30min`.

- Первые 30 минут — сон в RAM, быстрое пробуждение.
- Дальше система пишет образ RAM в зашифрованный swap 32 ГБ и выключается; при открытии
  крышки initrd снова спрашивает PIN. Голый suspend оставлял бы ключ LUKS в RAM.
- swap 32 ГБ = размер RAM: образ сжимается, но несжимаемые данные дают почти полный
  размер. Меньше — гибернация может отказать.

## 8. Граница и досмотр

Криптография защищает от копирования диска, но не от требования «разблокируйте».
Если ноутбук унесли и сняли SSD — там шифротекст. Если ты стоишь рядом и сам вводишь
PIN — шифрование бессильно; работает только «данных с собой нет».

Практика: полный `poweroff` перед поездкой (после suspend-then-hibernate есть окно
30 минут, когда поднятая крышка открывает систему без PIN); минимум данных на диске;
рабочие файлы — на VPS по SSH. Правовую оценку отказа давать не могу — это твоё решение.

## 9. Чего схема не защищает

- Угон включённого/разлоченного ноутбука: диск уже открыт, ключ в RAM.
- Вредоносный код под твоим пользователем.
- Фишинг, утечки через браузер и облака.
- Потерю данных: шифрование — про конфиденциальность, не про сохранность. Бэкапа нет —
  это принятый риск.

## 10. Итог

LUKS защищает диск, Secure Boot — загрузку от подмены, TPM+PIN убирает длинную фразу из
каждой загрузки, snapper даёт откат после неудачного обновления. Это четыре разные вещи;
включаются в порядке LUKS → Secure Boot → TPM → остальное.
